图 1 · 任务在多 Agent 系统中的流转

端到端 · 采集 → 协同 → 交付

三条泳道对应三个边界：m1 采集端、GraphQL 控制面 + worker 执行面、交付与审计。 阶段之间只传“上一阶段的最后一条消息”，不共享上下文；Executor 是唯一可写角色。

  1. 1手写表拍照后落入 m1 的 inbox/，原图不裁剪、不压缩。
  2. 2collect.sh 逐张调用 Agent（--single），跳过已存在产物。
  3. 3图片以 data URL 进入多模态消息，首个阶段直接可见原图。
  4. 4工具调用转发进容器，产物写入 data/<同名>.csv。
  5. 5CSV 落盘后校验非空，空响应或空文件按失败退出，需人工重跑。
  6. 6提交并推送远端，同时创建交接 Issue 供分析端领取。
  7. 7协调者先记 lastSeq 再 createTask，订阅时从该序号补齐，避免漏事件。
  8. 8worker 轮询到待办阶段后 claimStage 拿租约；他人持锁则跳过，掉线自动过期。
  9. 9阶段只接收“任务 + 上一阶段输出”，工具集按角色收敛（仅 Executor 可写）。
  10. 10Reviewer 不通过则回到 Executor，attempt 累加，超限转人工。
  11. 11通过后产物提交进远端仓库，按任务目录归档。
  12. 12交接 Issue 固化验收标准：列名、行数、统计口径都必须可复核。
  13. 13分析 Agent 消费 CSV，产出 summary.md 与 charts/*.png。
  14. 14独立审计复算并比对产物，结论只写“通过 / 返工”，不采信 Agent 自述。
同步调用（阶段推进 / 派单） 返工回路（reject → 重试） 泳道间交接 绿色框 = 终态与结论

图 2 · 信息在 GraphQL ↔ Redux 中的传递路线

命令下行 · 事件上行 · worker 闭环

三条数据通路：蓝色是命令下行（dispatch → mutation），绿色是事件回传（subscription → action → state）， 橙色是 worker 的执行闭环。任何跨机信息都先变成 action 再进 store，UI 只订阅 state。

  1. 1用户输入变成 agent/submit，先过 reducer 保证状态机合法。
  2. 2Saga 用 take 接住 action，决定本地执行还是远端模式。
  3. 3远端模式下 call RemoteClient，工具调用与网络细节都留在 Saga。
  4. 4createTask / claimStage / finishStage 走 mutation，查询走 query。
  5. 5服务端把任务、阶段、租约、事件序号收敛为唯一状态。
  6. 6订阅 events(since) 拿到增量事件流，socket 断开可自动重连补齐。
  7. 7eventChannel 用 expanding 缓冲，避免回放事件被固定容量丢弃。
  8. 8每条事件映射成既有 action（stageStarted / stageEnded / agentError…）。
  9. 9reducer 更新 state.stages 与消息数组，不产生副作用。
  10. 10渲染层只订阅 state，TUI 与行式渲染器行为一致。
  11. 11worker 轮询任务列表，挑出第一个未完成且未出错的阶段。
  12. 12claimStage 带 machineId 与租约时长；抢不到说明前序未完成或他人持锁。
  13. 13本机跑真实模型与工具，文件读写进沙箱容器，产物路径必须在任务目录内。
  14. 14finishStage 带 version 做 CAS，成功后追加事件并广播给所有订阅者。
命令下行（dispatch / mutation） 事件上行（subscription → action） worker 执行闭环（租约 / 工具） SSE 长连接

说明：图 1 的返工回路与阶段验收按当前实现绘制（Reviewer 输出判定，attempt 上限 2）； P2 的 evidence / accept-reject 门禁、P3 的入料校验仍属规划态，尚未进入主链路。 图 2 中 lastSeq、expanding()、version CAS 均为现有实现， 对应 src/store/remote.ts、src/remote/graphql.ts、poc/server.ts。
